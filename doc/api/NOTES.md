## Running it

```clojure
;; config.edn :addons {"hive.compose" {...}}
:compose/api {:enabled? true :port 0 :host "127.0.0.1"}   ; additive; off by default
```
- `:port 0` binds an ephemeral port. `compose status` answers `api {host port url}`, and so does the initialize! metadata. A bind failure, or a non-loopback `:host` (refused), leaves the addon running and puts `api {error detail}` in its state.
- The server starts in `initialize!` after the reaper and stops in `shutdown!`, 4 daemon threads, request bodies are capped at 1 MiB (413).
- `curl -s -XPOST -H 'Content-Type: application/json' 127.0.0.1:$PORT/v1/status -d '{}'` (a POST without that header is 415), `curl 127.0.0.1:$PORT/v1/openapi.yaml`, `curl 127.0.0.1:$PORT/v1/health`.

## Implementation

- `hive-compose.addon/dispatch` (was private) is the ONE dispatch: the MCP tool handler and the API both call `(dispatch addon command params)`. The MCP behaviour did not change: same params, same `text-result`, bare categories.
- `hive-compose.api/route` maps (method, path, body) to {status headers body}. `POST /v1/{command}`, with the body a JSON object (blank = `{}`, a `command` key is ignored; the path names it). A planned path answers 501 `compose/not-implemented`, and an unknown command 404 `compose/unknown-command`. Both are checked before dispatch, so they do not depend on the lifecycle. A thrown dispatch answers 500 `compose/dispatch-threw`.
- Envelope: `{ok:true,value}` | `{ok:false,error,...}`. Every `:error` keyword at any depth is written qualified (`api/qualify-errors`), and every other key or value goes through the same `data.json` encoder as MCP (namespaced keys bare).
- Browser guard (`api/browser-guard`, before anything else): binding loopback does not stop a web page, which can POST `text/plain` with no preflight and use DNS rebinding to read answers. So the guard refuses with 403 `compose/forbidden-origin` when Host is not 127.0.0.1, localhost or [::1], or when an Origin header is present and not loopback. A POST without `Content-Type: application/json` gets 415 `compose/unsupported-media-type`; that header forces a CORS preflight, and the server never grants one.
- Param types (`api/check-params`): a declared tool param of the wrong JSON type (tail "many", env "x") gets 400 `compose/invalid-param` before dispatch. Booleans also accept "true"/"false", as on MCP.
- A throw, in dispatch or around it, is answered as the envelope (`compose/dispatch-threw` or `compose/internal`) with only the class and message, never ex-data, which could carry env values.
- Bad `:compose/api` values never fail the addon. That covers a non-loopback host, a port outside 0..65535, threads below 1, and a bind error. `status` then answers `api {error detail}`. A changed `:compose/api` is listed under `reload`'s `:not-reloaded`, because it is rebound at the next initialize!.
- **Trust model**: there is no auth. Every local process is the operator. `agent`/`agent_id` are taken as sent, so any local caller can claim or release for any agent. That is the same as MCP today, where the host stamps agent_id. A token file is the next step if a non-operator process ever shares the host.
- Status: 400 missing/invalid-param; 403 forbidden-origin; 415 unsupported-media-type; 404 unknown-command/route/profile/target/project, no-projects; 405 non-POST on a command; 409 not-active, not-claimed, orphans-hold-resources, held-by-another-section; 413; 501 planned; 502 command-failed, secret-unresolved, secrets/unknown-backend; 503 not-initialized, invalid-config; 500 anything else. Since the stack, faults and why merges, `status-by-category` maps every category the source answers: 400 invalid, unknown-reference, clash and collision; 404 a named run, stack, test or proxy not there; 409 conflict or exists; 502 a backend (docker, toxiproxy, the trace store) failed or is unreachable; 503 not ready or not configured; 500 a fault of the addon. NB: unknown-command moved from the draft's 400 to 404 (card decision).

## Design

- `POST /v1/{command}` with body = the MCP params minus `command`. `x-hive-call-op` on each operation is the `op` for `hive_call(op, json)`, and the body is the same JSON, so both transports share one request schema.
- Responses use the hive-cabi/v1 envelope (`hive-spi.native.schema/Envelope`): `{ok:true, value}` | `{ok:false, error:"<category>", ...rest of the r/err map}`. hive-spi's Envelope is an open map, so the extra keys (`param`, `profile`, `known`, `hint`, `stderr`, `holders`, `orphans`) conform. `error/type` is reserved for host transport failures (`native/*`).
- The HTTP status codes are a proposal: 400 bad or missing param and unknown command, 404 unknown target/profile/project, 409 not-active, not-claimed and the two guard refusals, 502 compose command failed or secret unresolved, 503 not-initialized or invalid config. The body is always the envelope, so a client can ignore the codes, and hive_call has none.
- `x-mutates` flags commands with side effects (all are POST, including the reads, so the op name stays the whole route).

## JSON key naming (decision for the draft)

**The draft uses bare names (namespace dropped), because that is what both sides already do:**
- On the wire, the tool's `clojure.data.json/write-str` writes `:profile/id` as `"id"` and the keyword value `:compose/unknown-profile` as `"unknown-profile"`. Measured with `gen/staging.datajson-probe.json`.
- `malli.json-schema` likewise emits `"id"` for `:profile/id`.

hc-lane-edge suggested "without the ns or with a/b style". I chose without the ns for the value objects, because it matches today's wire. Exceptions:
- **Error categories are qualified (`compose/unknown-profile`) on the API wire**, while the MCP text keeps `"unknown-profile"`. DECIDED by coordinator:45a1f993 (open question 1 closed), implemented with no MCP change.
- `Report.cases[].case/id` keeps hc-8's `a/b` style as relayed by hc-lane-core.

**Risk of dropping the ns:** collisions. The probe map `{:profile/id "x" :program/id "p"}` serialised to **two `"id"` keys** in one object. No current response puts two `*/id` keys in one map (checked by reading ops/swarm), but hc-6 Instance/Wiring rows will be next to `profile/id`. The fix is to serialise with `:key-fn` keeping `ns/name` in the HTTP adapter. That changes the MCP wire too unless it is done only in the new transport.

## Issues found while generating clients (all fixed in assemble.py unless noted)

1. **openapi-typescript and `anyOf [{required:[target]},{required:[profile]}]`**: each required-only branch became `unknown`, collapsing the whole body type to `unknown`. I dropped it for `x-requires-one-of: [target, profile]`, so the target-or-profile rule is not machine-checked (the server answers `missing-param`).
2. **elm-open-api cannot follow `$ref` into another schema's properties** (`#/components/schemas/ComposeRequest/properties/x`). Param schemas are now inlined per command.
3. **Elm shadowing**: the component `Error` generated `decodeError`, which collides with a local name in generated code, and Elm 0.19.3 rejects shadowing. Renamed to `ErrorEnvelope`.
4. Elm is lossy for `anyOf string | object` and `const`. `Env` becomes `Dict String Json.Encode.Value`, `ok` becomes `Value`, `error` becomes `Value`, and `holds` becomes `{}`. It works, but Elm callers build the SecretRef by hand. **Not fixed.** A `oneOf` with a discriminator is impossible here because the string branch has no property. Possible fix: a dedicated `{literal: s} | {pass: p}` form for the HTTP API only (open question 3).
5. malli 0.20's json-schema leaves `:re` patterns as `java.util.regex.Pattern`, so gen.clj renders them with `str`. `[:fn ...]` parts (the Suite image-or-command rule) are dropped, and `[:and number? [:>= 0]]` (cpu-busy-percent) becomes a bare `{}`/number without the bound. Check after hc-2 merges.
6. Booleans: MCP accepts `"true"` strings (`addon/flag`), while the draft types them as boolean. An HTTP adapter should accept both or reject strings; I left it as a note in the ComposeRequest description.

## Gaps

- No response schema is enforced in source. They are hand-copied and will drift. Proposal: when hc-14 is built, add malli schemas for the result maps in a `schema/api.clj`, `m/=>` the dispatch results in tests, and generate everything.
- `logs.out` is one string (compose output, clipped by `cli/max-output-chars`), not per-service lines.
- The `status.config[].error` and `StepReport.error` inner shapes are loose (`select-keys res [:error :exit :stderr]`).
- `who.agents[]` comes from ISwarm `{agent/id agent/status agent/cwd}` plus `sections`. It is typed open.
- `reap` returns the `tick!` pass with `{skipped}` and `{error}` variants under ok:true. A thrown pass is still ok:true with `error` inside, which a client could mistake for success.
- The MCP `help` works before init, and everything else answers not-initialized (503). The HTTP server only runs while the addon is active, so over HTTP a 503 appears only between a failed reload and the next init.
- There is no auth or security scheme. The MCP host stamps `agent_id`, but an HTTP server needs an identity for `claim`/`release` (agent defaults to agent_id).
- `hive_call` is designed below, not built (phase 2).

## Phase 2: hive_call(op, json) onto the same dispatch (design, out of scope for this PR)

`hive_call(op, json)` (hive-cabi/v1) is a second transport over the SAME function the HTTP adapter calls:

```
hive_call(op, json)  ==  (api/encode (api/envelope (api/call deps op (json/read-str json))))
POST /v1/{op}        ==  the same, plus api/http-status for the code
```
- `op` is the operation's `x-hive-call-op`: the command name for today's paths, dotted for the planned ones (`stack.up` maps to `/v1/stack/up`; `api/planned` holds the table). `json` is the request body unchanged, so both transports share one request schema. The answer is the envelope with no status code. Host-side failures use `error/type` `native/*` (unavailable, timeout, malformed, failed) and never a `compose/*` category.
- `ops` catalog: generated from the spec, with name = x-hive-call-op, doc = summary, pure = (not x-mutates).
- Where it runs:
  - **In the hive JVM** there is no native step. A caller already holds the addon, so `api/call` with `(partial addon/dispatch a)` is the in-process hive_call. A JVM `hive_call` shim over FFM is only needed for a foreign .so.
  - **Non-JVM callers** (Go, Rust, Node via koffi) either use HTTP, or load a native library exporting `hive_call`/`hive_free`. The hc-15(b) spike (knowledge 20261122142916-4a4b1c4b) built one with jolt: a 16.5 KB C shim (real dynamic symbols, dlopen of the 15 MB jolt .so, `jolt_library_init` once, `:collect-safe` exports, malloc'd strings freed by `hive_free`). Its output was byte-identical to the JVM's. Only the PURE layer can go there (resolver/plan: hc-3/hc-4). Docker-driving commands stay in the JVM and are reached over HTTP. Keep hc-3/hc-4 portable .cljc so this stays open.
  - **A jolt .so loaded INTO a JVM crashes the JVM** (Chez signal handlers clobber the JVM's) unless the JVM is started with `LD_PRELOAD=$JAVA_HOME/lib/libjsig.so`. hive-cabi's JVM loader must set or require that for jolt libraries (see the hive-cabi README). Inside hive-mcp, prefer the HTTP API or a subprocess.
- Blocking: hive_call is synchronous, as HTTP is. `up --wait` can take `:compose/up-timeout-ms` (10 min), so a native caller runs it on its own thread. A deadline param (`timeout_ms` in the body) is a later addition for both transports at once.
- Identity: the MCP host stamps `agent_id`. Over HTTP and hive_call, `claim`/`release` need `agent` in the body (otherwise `compose/missing-param`). There is no auth: the API binds loopback only.

## Follow-ups (from review, not in this PR)

- `(str t)` of an ExceptionInfo still prints its ex-data in `addon/tick!` last-pass (`status`, `reap`), `ops` release-threw, `orphans`/`ownership` check-failed. This predates hc-14 but now reaches HTTP: switch to class + ex-message.
- The pool has 4 threads with an unbounded queue and no read timeout. A slow client or four `up --wait` calls starve `/v1/health`. Bound the queue (503) and set `sun.net.httpserver.maxReqTime`.
- A changed `:compose/api` is only reported by reload, not rebound, and the comparison is against the last reload's cfg, not the config the server started with.
- `check-params` runs before the unknown/planned check, so a badly typed param on `/v1/bogus` answers 400, not 404.
- The spec does not declare 405/413 responses yet.
- `gen/hc2.*.json` came from the uncommitted hc-2 worktree. Regenerate it from `origin/feat/hc-2-stack-schema` b55bf75 (or staging, once hc-2 merges) and pin the commit in assemble.py.
- When hc-6 (PR #47) lands: `stack-up`, `stack-down`, `stack-status` and `plan` become real paths, and the contract test picks them up from the command enum.
